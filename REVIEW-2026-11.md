# needalab.com code review, 2026-11-01

Read-only review of `main` at 3f16c79. Scope: index.html, js/account.js, js/stemrankings.js, scripts/build-topics.mjs, all of supabase/functions, all of supabase/migrations. Nothing was edited, committed, or deployed.

Lenses applied: thermo-nuclear-review (security + correctness), thermo-nuclear-code-quality-review, deslop, ponytail-review, and first-principles ("should this exist, is it simpler than it could be").

Every Critical and High was traced end to end in the code. Items I could not confirm were dropped or downgraded with the confidence noted.

Overall: this is a small (about 3,500 lines), unusually careful codebase. The money path is sound: `spend_credits` is atomic, every failure path in `draft` refunds, `grant_credits` is idempotent on `ref`, the Stripe webhook verifies the signature with a timestamp window and a constant-time compare, and RLS is on every table with grants revoked where the browser should not see rows. I found no Critical issues and no XSS. The real risks are quota and abuse edges, not money loss.

## Keep as is (checked, correct)

- `spend_credits` / `grant_credits`: atomic balance update with `credits_cents >= p_cost` guard, ledger insert, unique `ref` for idempotency, execute revoked from anon/authenticated, granted to service_role only. Refund refs are `refund:<uuid>`, so refunds never collide with invoice grants.
- `draft` refund discipline: every non-success path after `spend_credits` refunds, including the streaming path's malformed and exception branches; client disconnect is swallowed at `enqueue` so the refund or the insert still runs. Live test (tests/refund.test.mjs) covers charge-then-refund against the real API.
- `stripe-webhook`: raw body HMAC with 300s tolerance, constant-time compare, idempotent grant keyed on `invoice:<id>`, `amount_paid > 0` check, user resolved from signed subscription metadata then by stored customer id, 500 on grant error so Stripe retries, 200 on unknown events.
- `billing`: customer id saved before redirect, age gate enforced server-side, secrets never leave the function.
- RLS: every table has RLS on; `openalex_cache`, `search_quota`, `crm_contacts`, `gmail_connections` have no policies and all grants revoked; `drafts` insert/update and `credit_ledger` writes revoked; `profiles` update limited to `display_name, birth_year` by column grant; `crm_users` revoked from anon/authenticated; `handle_new_user` and `is_age_ok` are `security definer` with empty search_path.
- Gmail token at rest: AES-GCM, random 12-byte IV per encryption, key derived from `GMAIL_TOKEN_KEY` via SHA-256, decrypt only server-side. Header injection stripped in `sanitizeHeader`, recipient re-read from the DB.
- XSS: every interpolation of user, OpenAlex, find-email, and AI-draft data in account.js and stemrankings.js goes through `esc`/`escHtml` or `textContent`, including the AI subject/body in `showDraft` and the streamed preview (`pre.textContent`). Dates and counts come from typed columns. The rankings' `csr.toggleFaculty('${e}')` uses `encodeURIComponent`, so apostrophes in "Xi'an Jiaotong University" cannot break out. One unescaped `orcid` in an href noted above as Low.
- `find` quota: `take_search` is an atomic upsert, only charged on cache miss, keyed per user or per /24.
- Age gate: enforced in RLS policies and re-checked in `draft`, `billing`, `gmail` because the service role bypasses RLS. Birth year locked after first set.
- `_shared/openalex.ts` `cached()`: never caches empty results, cache failures never fail the request.
- Pure-logic modules (`rank.ts`, `summarize.ts`, `pipeline.ts`, `rules.ts`, `mail.ts`) are separated from I/O and have unit tests.
- `users.csv` is gitignored and untracked; `export-users.sh` reads the CLI token from the keychain rather than a file.
